[배포]
// dist/linux-x64 폴더를 통째로 복사하면 끝이다. 두 파일이 같은 폴더에만 있으면 된다.
//   HeliosenGltfpack
//   libHeliosenGltfpack.so
//
// 실행파일 rpath 가 $ORIGIN 이라 설치 경로에 상관없이 옆의 .so 를 찾는다.
// LD_LIBRARY_PATH 설정이나 ldconfig 등록이 필요 없다.
//
// 대상 머신에 아래는 있어야 한다 (ubuntu 22.04 기준 기본 포함).
//   libzstd.so.1  libstdc++.so.6  libm.so.6  libgcc_s.so.1  libc.so.6
// 확인 : ldd dist/linux-x64/HeliosenGltfpack

// C# 등에서 라이브러리로 쓸 때는 libHeliosenGltfpack.so 만 가져가서
// CallMain(int argc, char** argv) 를 P/Invoke 하면 된다. 런처는 필요 없다.


[모듈 이름 잠금(License) 검증]
// gltf/gltfpack.cpp 의 checkModuleName() 이 모듈 파일명을 확인한다.
//   Linux   : libHeliosenGltfpack
//   Windows : heliosen.gltfpack   (소문자화 + 확장자 제거라 dll/exe 공통)
// 틀리면 "Error: invalid user." 출력 후 exit(1).
//
// 중요. 검사 대상은 실행파일 이름이 아니라 gltfMain() 이 들어있는 모듈의 파일명이다.
//       dladdr((void*)&gltfMain, ...) 이 돌려주는 값을 본다.
//       => 런처가 .so 를 동적 링크하면 dladdr 이 .so 를 가리켜 통과한다.
//          그래서 실행파일 이름은 아무거나 상관없다.
//       => 반대로 gltf 소스를 실행파일에 정적으로 링크하면 dladdr 이 실행파일 자신을
//          가리켜서 잠금에 걸린다. MESHOPT_BUILD_GLTFPACK=ON 으로 만드는 upstream
//          gltfpack 실행파일이 바로 이 경우라 쓸 수 없다.
//
// 주의. cp 로 .so 파일 이름만 바꿔 링크하면 검증이 안 된다.
//       .so 안에 SONAME=libHeliosenGltfpack.so 가 박혀 있어서 링커가 파일명이 아니라
//       SONAME 을 DT_NEEDED 에 기록하고, 실행시엔 결국 정상 .so 를 물어와 통과해 버린다.
//       => soname 까지 바꿔서 다시 링크해야 한다.

cd build_linux
sed -e 's/-Wl,-soname,libHeliosenGltfpack\.so/-Wl,-soname,libWRONG.so/' \
    -e 's/-o libHeliosenGltfpack\.so/-o libWRONG.so/' \
    CMakeFiles/CCdMeshOptimizer.dir/link.txt > link_wrong.sh
sh link_wrong.sh
gcc ../CCd.MeshOptimizerLinux/launcher.cpp -I../CCd.MeshOptimizerLinux \
    -L. -lWRONG -Wl,-rpath,'$ORIGIN' -o test_wrong
readelf -d test_wrong | grep NEEDED
// -> libWRONG.so 여야 한다.
//    libHeliosenGltfpack.so 로 나오면 위 sed 가 안 먹은 것이라 검증이 무의미하다.

./test_wrong -i ../test/data/tree.glb -o /tmp/wrong.glb -c -tc
// -> "Error: invalid user." 가 뜨고 exit=1 이어야 정상.
//    압축이 되면 잠금이 깨진 것이다.

// 검증이 끝나면 잔재를 반드시 지운다.
// 남겨두면 다음 빌드 때 링커가 엉뚱한 .so 를 집어가는 사고의 원인이 된다.
rm -f libWRONG.so link_wrong.sh test_wrong
cd ..

[Docker 운영 - 상주 컨테이너 + exec]
// 중요. 매 호출마다 docker run 을 쓰면 안 된다. 컨테이너 생성 부하가 계산시간보다 비싸다.
//
// 실측 (tree.glb 281KB, 중앙값)
//   컨테이너 내부 순수 계산        277 ms    <- 네이티브 277ms 와 동일. 계산 저하 없음.
//   docker exec 로 호출            +약 17 ms
//   docker run --rm 로 매번 호출   +약 400 ms   (컨테이너 생성 + 파괴)
//
// 그래서 컨테이너는 한 번만 띄우고 exec 로 때린다.
docker run -d --name heliosen-gltfpack --restart unless-stopped \
    -v /srv/models:/work heliosen-gltfpack

docker exec heliosen-gltfpack HeliosenGltfpack -i /work/in.glb -o /work/out.glb -c -tc

// 로딩 확인
docker exec heliosen-gltfpack HeliosenGltfpack --selftest

// 결과물 소유권을 호스트 사용자로 맞추려면 --user 를 준다. (안 주면 root 소유가 된다)
docker exec --user $(id -u):$(id -g) heliosen-gltfpack \
    HeliosenGltfpack -i /work/in.glb -o /work/out.glb -c -tc

// 일회성 실행도 되지만 위 400ms 부하가 매번 붙는다.
docker run --rm -v /srv/models:/work heliosen-gltfpack \
    HeliosenGltfpack -i /work/in.glb -o /work/out.glb -c -tc
